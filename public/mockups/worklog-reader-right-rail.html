Design decisions baked into this mockup (these are the trade-offs the ADR will lock)

1 · Rail is desktop-only (xl+) Decision

Below xl the reader falls back to a single floating "open context" button (top-right of the reader toolbar) that opens a bottom-sheet with horizontal tabs. Today's inline stacked layout is gone on mobile too — we don't want two truths for "where does Backlinks live." The mockup's bottom-sheet matches the existing drawer pattern used elsewhere in the app.

2 · Four tabs at launch: Backlinks · History · Tags · Photos Decision

Tags and Photos move into the rail too — the cheap promotion is "anything that's not the note body itself." This makes the reader body just the note. The parked entry only mentioned Backlinks + History + ToC; promoting Tags/Photos is the additional decision worth flagging here. → Reader body becomes leaner (~150px of vertical scroll reclaimed on a 3-paragraph note).

3 · Table of contents is deferred Trade-off

Shown greyed in the strip. The parked entry leaned on "ToC needs a home" but our notes today are too short — a 2-paragraph note with a ToC is noise. Auto-show ToC tab when note has 4+ headings or 800+ words. Until either threshold, the tab is hidden entirely.

4 · Persistence: per-user, not per-note Trade-off

Active tab + collapsed state stored in WorkLogPreference (existing table). Per-user means: if you set History as your default tab, every note opens to History. Per-note persistence is rejected for v1 — too much state, no real upside (Tolaria also goes per-user).

5 · Keyboard: ⌘1–4 to switch, ⌘\ to collapse Decision

Surfaced in the status bar (visible in the mockup). Same shortcut pattern as VS Code's sidebar tabs. Numbers map to the visible tabs in order, so when ToC unlocks later, ⌘5 becomes ToC.

6 · AGPL boundary: patterns only, no Tolaria source Hard gate

The implementation will be written from scratch against our existing components (WorklogBacklinksPanel, WorklogHistoryPanel) wrapped in a new NoteContextRail container. We will read Tolaria's docs/ARCHITECTURE.md "Four-Panel Layout" section for design reference. No JSX, hooks, or utility functions will be copied.

7 · Status bar quietly snuck in Scope check

The bottom row showing version / word count / keyboard hints is parked tolaria #3, not part of this ADR. Shown here only because the keyboard-hint row is a natural fit. If status bar isn't approved separately, the keyboard hints get a small inline tooltip on rail hover instead. → Flag in the ADR — don't ship #3 as a free rider on #1.

8 · Edit mode behavior Open question

When the user enters edit mode (Tiptap editor), does the rail stay open or auto-collapse to give the editor full width? Proposal: stay open — Backlinks visible while editing is actually useful (you can see what links here). User can collapse manually if they want full width.

9 · No-selection mode: list claims the full width, rail auto-hides Decision

When no note is selected, the reader pane and the rail both collapse so the list can claim the full horizontal space (see Frame 2 above). The wider list gains a 3rd column for tag chips, longer titles, full preview snippets, and date-grouped headers — giving the user a real "see everything at once" view instead of a narrow 288px column. A 7px ghost-rail at the far right stays visible as a reminder that the rail isn't gone, just idle. Picking any row re-mounts both the reader and the rail to today's tab/state. → The deselect transition (click active row, or EscEsc) plays the same animation in reverse.
