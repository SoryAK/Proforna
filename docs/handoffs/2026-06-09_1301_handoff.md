## The "Live" Context

**Recovery flow that worked (now codified in
`docs/workflows/recover-from-prisma-drift.md`):**

1. Confirm `migrate status` is clean (history-vs-DB table check passes).
2. Create shadow DB on same Postgres instance (same host/creds, different
   name).
3. `prisma migrate diff --from-migrations prisma/migrations
   --to-schema-datamodel prisma/schema.prisma --shadow-database-url ...
   --script > drift.sql`.
4. **Sanitize drift.sql** — skip the intrinsic
   `ALTER COLUMN "search_vector" DROP DEFAULT` false-positive (would break
   fresh deploy on Postgres), reorder for FK safety, add header comment
   referencing every ADR/sprint source.
5. Drop into `prisma/migrations/YYYYMMDDHHMMSS_baseline_drift_capture/migration.sql`.
6. `prisma migrate resolve --applied "<dir_name>"` on live DB (marks
   applied, does NOT re-execute).
7. Drop + recreate shadow → `prisma migrate deploy` from empty → confirm
   "up to date".

**Permanent gotcha (won't go away):** `Unsupported("tsvector")?` columns
will always show up in `prisma migrate diff` as `DROP DEFAULT` noise.
Prisma can't express the GENERATED expression in `schema.prisma`. Ignore
the line; do not include it in any migration.

**Convention going forward:** Never use `prisma db execute` for column or
table changes. Always author a real dated migration file via
`prisma migrate dev --create-only`. The db-execute workaround was a
pragmatic crutch during drift and using it again would recreate the same
problem.
